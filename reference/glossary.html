Reference · Automotive SPICE 4.1

Glossary

The course's vocabulary. Each term is used in exactly this sense in every lesson; the words to avoid are common near-synonyms that blur a distinction.

The model

PRM (process reference model): the set of processes, each with a purpose and outcomes. Avoid: "the standard".

PAM (process assessment model): the PRM plus the indicators an assessor uses to rate it. Avoid: "the checklist".

Process: in the PAM, a "distinct conceptual silo" of related goals, not a workflow or a lifecycle phase.

WHAT / HOW / DOING: goals (the PAM) / methods and tools / actual performance on real work.

Purpose: the one-sentence reason a process exists.

Outcome: an observable result of achieving the purpose. PA 1.1 rates outcomes.

VDA Scope: the recommended assessment scope: MAN.3, SUP.1, SUP.8, SUP.9, SUP.10 plus at least one engineering plug-in.

Plug-in: a domain's engineering processes (SWE, SYS, HWE, MLE) added under the domain-independent management and support processes.

Indicators

Base practice (BP): a process-specific activity indicator for level 1.

Generic practice (GP): an activity indicator for a process attribute, applied identically to every process.

Information item (II): what an assessor looks for, described by its characteristics in Annex B. Avoid: "required document".

Work product: what the organisation actually produced, including tool records such as Jira tickets.

Objective evidence: work products and testimony, the only two sources a rating may rest on.

The capability dimension

Capability level: 0–5, derived from PA ratings for one process. Avoid: "maturity level", which rates organisations in other models.

Process attribute (PA): a measurable property of capability; nine in total, two per level from 2 to 5.

N / P / L / F: not (≤15 %), partially (≤50 %), largely (≤85 %), fully (>85 %) achieved.

Level rule: level n needs its own PAs at L or F and every lower PA at F.

Process performance objective: a target for how one process is performed (GP 2.1.1). Not a project goal, not a restated outcome.

Standard process: the organisation-wide reference process, with tailoring guidelines (PA 3.1).

Defined process: a project's tailored instance of the standard process (PA 3.2).

Tailoring guideline: predefined, unambiguous criteria for deriving a defined process, with who tailors and who approves.

Engineering

Bidirectional traceability: links that can be followed both ways between related items. Avoid: using it to mean "consistent".

Consistency: linked items actually agree in content. Links alone don't prove it.

Verification measure: any check against a specification (test, review, analysis). ASPICE 4 says "verification" rather than "testing".

Validation (VAL.1): showing that the end product meets its users' intended-use expectations in its operational environment. The test is not whether a requirement exists but whether objective measurement settles it (verification) or it takes end users' judgement (validation). Not applied to pure embedded software or ECUs.

Stakeholder requirement (SYS.1): an agreed requirement from a stakeholder such as the customer. System requirements (SYS.2) are derived from them.

Software component: what the software architecture (SWE.2) decomposes the software into, down to the lowest-level components.

Software unit: what the detailed design (SWE.3) decomposes a component into, not subdivided further. First a design idea, not a file or function; under verification it is represented by source code or object files.

Software element: a component or unit, as something that is integrated (SWE.5).

Special characteristic: a property of a non-software system element derived in the system architecture (SYS.3.BP3), communicated to all affected parties.

Problem (SUP.9): something wrong, to be analysed and tracked to closure.

Change request (SUP.10): a wanted change, to be analysed, approved before implementation and traced to what it affects.

Baseline: a defined, consistent, read-only set of configuration items at a point in time.

Configuration item: a work product, or group of them, managed as one entity under SUP.8. With AI assistance this can include prompts, models and their settings.

Lifecycle: the project's own phases, gates and order (MAN.3.BP2), a HOW. ASPICE defines none. Avoid: "ASPICE phases".

Release approval (SPL.2.BP5): approval against release criteria before delivery, naming the approver and their role.

Assessment

Assessment scope: org-unit boundaries, processes, target level per process, and process context.

Process context: the factors bounding what is rated, such as releases, components and inclusions.

Process instance: one distinct way a process is performed within the scope, rated separately and then aggregated.

Aggregation: the mean of instance ratings as N0 P1 L2 F3, where exactly halfway rounds up.

Rating rule (RL): a Guideline directive such as "shall (not) be downrated" or "not higher than".

Weakness statement: what is missing, the traceable evidence, and the process risk. Required for every downrating.

Abbreviations and names

CCB (change control board): the body that approves change requests (SUP.10.BP3).

Flex process: a process outside the base of the recommended VDA Scope, added when the assessment purpose needs it (e.g. SPL.2, VAL.1, MAN.5).

Gate4SPICE: the regular talks run by intacs, the assessor certification body.

HIL (hardware-in-the-loop): testing software on the real ECU against a simulated environment.

RASIC: a matrix saying who is Responsible, Approves, Supports, is Informed or Consulted for each activity (GP 3.1.1).
